# ARM64 JIT Critical Bug: Missing Argument Load to hl_type_get_global()

## Status: ACTIVE BUG (2025-01-19)

**Severity:** CRITICAL - Prevents all HashLink programs from running on ARM64
**Symptom:** Segmentation fault in `hl_type_get_global()` with NULL pointer argument
**Impact:** Hello World and all other HashLink programs crash immediately during type initialization

---

## Previous Bug: X29 Frame Pointer Corruption ✅ FIXED

Before investigating this bug, we fixed a critical X29 (frame pointer) corruption issue:
- **Problem:** Native C functions were corrupting X29 to invalid values like 0x1
- **Solution:** "Nuclear approach" - add `ADD X29, SP, #0` after EVERY BL/BLR instruction
- **Result:** X29 corruption completely eliminated
- **Commit:** d19fea8, e517834, c942be8

With X29 fixed, the program progresses further and now crashes on a different bug.

---

## Technical Analysis

### 1. Function Signature

```c
// From src/std/types.c:477
HL_PRIM vdynamic *hl_type_get_global( hl_type *t );
```

Takes one argument: `hl_type *t` (should be passed in X0 per ARM64 AAPCS)

### 2. Caller Analysis

**Caller Address:** `0x00007ffff5c37ea0` (JIT-compiled code)

**Disassembly of Caller:**
```asm
0x7ffff5c37e78:  stp   x29, x30, [sp, #-96]!   # Prologue: save FP/LR, alloc 96 bytes
0x7ffff5c37e7c:  mov   x29, sp                 # Set FP = SP
0x7ffff5c37e80:  stur  x0, [x29, #-8]          # Save arg0 to stack [FP-8]
0x7ffff5c37e84:  stur  x1, [x29, #-16]         # Save arg1 to stack [FP-16]
0x7ffff5c37e88:  stur  x2, [x29, #-24]         # Save arg2 to stack [FP-24]
0x7ffff5c37e8c:  stur  x0, [x29, #-16]         # Save arg0 again at [FP-16] (odd!)
0x7ffff5c37e90:  mov   x9, #0xf780             # \
0x7ffff5c37e94:  movk  x9, #0xf7f4, lsl #16    #  > Load hl_type_get_global address
0x7ffff5c37e98:  movk  x9, #0x7fff, lsl #32    # /
0x7ffff5c37e9c:  blr   x9                      # ← CALL - but X0 never loaded!
0x7ffff5c37ea0:  mov   x29, sp                 # Restore X29 (our nuclear fix)
```

**Critical Problem:** No `ldur x0, [x29, #offset]` instruction before the BLR!

### 3. Expected vs Actual Code

**EXPECTED code pattern (with argument load):**
```asm
ldur  x0, [x29, #-N]      # Load hl_type* from vreg on stack
mov   x9, #0xf780         # Load function address
movk  x9, #0xf7f4, lsl #16
movk  x9, #0x7fff, lsl #32
blr   x9                   # Call with valid X0
```

**ACTUAL code pattern (missing argument load):**
```asm
                          # ← X0 load is MISSING!
mov   x9, #0xf780
movk  x9, #0xf7f4, lsl #16
movk  x9, #0x7fff, lsl #32
blr   x9                   # Call with X0=0 (whatever it was before)
```

### 4. Function Context

**Frame Size:** 96 bytes (from `stp x29, x30, [sp, #-96]!`)

**Likely Function:** Based on frame size 96 and calling `hl_type_get_global`, this is probably:
- Function 290 (`$Type`) - Type initialization function
- Or Function 295 (`$Type`) - Also type initialization

These functions are automatically generated by the Haxe compiler for static class initialization and would naturally call `hl_type_get_global()` to get the global value for a type.

## Root Cause Hypotheses

### Hypothesis 1: Wrong Opcode Handler

The call might be generated by an opcode other than OCall1:
- **OCall0:** Takes 0 arguments, wouldn't load X0 (but hl_type_get_global needs 1 arg!)
- **OCall2-4:** Take multiple arguments
- **OCallN:** Variable arguments
- **OCallMethod/This/Closure:** Dynamic dispatch

**Evidence Against:** OCall1 handler at src/jit.c:4535 HAS the load:
```c
vreg *arg = R(o->p3);
if (arg) LOAD_VREG(X0, arg);
```

### Hypothesis 2: NULL vreg Pointer

The `arg` pointer from `R(o->p3)` might be NULL:
- If `o->p3` is out of bounds
- If vreg allocation failed
- If the bytecode is malformed

**Evidence Against:** The code checks `if (arg)` before loading, so a NULL vreg would skip the load entirely. But we see attempts to load the function address, suggesting the call is being generated.

### Hypothesis 3: vreg Contains NULL

The vreg exists but contains a NULL value:
- A previous opcode wrote NULL to the vreg
- The vreg was never initialized
- Type information is missing/corrupted

**Most Likely:** The vreg is valid, the load happens, but the VALUE in the vreg is NULL/0.

### Hypothesis 4: Bytecode Signature Mismatch

The HashLink bytecode might declare `hl_type_get_global` as taking 0 arguments, but the native C function actually needs 1 argument:
- Bytecode: `OCall0` → no argument load
- Native: `hl_type_get_global(hl_type*)` → expects argument in X0

**Evidence:** Need to check function registration and signature in bytecode.

## Historical Context

This bug was discovered after fixing the X29 frame pointer corruption bug. The X29 fix allowed execution to progress further, revealing this deeper issue with argument passing to native functions. This represents the second major blocker in the ARM64 JIT port, and fixing it should allow basic HashLink programs to execute successfully.
