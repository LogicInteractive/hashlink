# ARM64 JIT Memory Corruption Bug

## Summary
HashLink crashes with segfault when running Hello World on ARM64 Raspberry Pi 5. Investigation reveals JIT code buffer corruption with invalid instructions containing huge stack offsets.

## Crash Details

**Location:** `0x7ffff5c37e14` in JIT-generated code
**Instruction:** `0xf91f83aa` = `LDR X10, [X29, #16128]`
**Registers at crash:**
- X29 (frame pointer) = `0x7fffffffee90` (valid stack address)
- X10 = `0x0` (NULL)
- Access address: `0x7fffffffee90 + 16128 = 0x7ffffffff790` (beyond stack!)

## Evidence of Corruption

Disassembly around crash shows clearly corrupted code:

```assembly
0x7ffff5c37de4:  mov x29, sp
0x7ffff5c37de8:  mov x29, sp    <- THREE identical instructions!
0x7ffff5c37dec:  str x0, [x29, #16128]   <- Huge offset #1

0x7ffff5c37e14:  str x10, [x29, #16128]  <- CRASH HERE (actually LDR)
0x7ffff5c37e24:  str x0, [x29, #16096]   <- Huge offset #3

0x7ffff5c37e40:  mov x29, sp
0x7ffff5c37e44:  mov x29, sp    <- THREE more identical instructions!
0x7ffff5c37e48:  mov x29, sp
```

**Normal function prologue:** ONE `mov x29, sp` after `stp x29, x30, [sp, #-N]!`
**Seen here:** THREE `mov x29, sp` in a row - clearly wrong!

## Investigation Results

### 1. Instruction Decoding Discrepancy

GDB disassembles crash instruction as "str" but actual bytes are LDR:

```
Bytes: 0xf91f83aa
Decoded:
  - Opcode [31:24]: 0xF9 (LDR, not STR!)
  - imm12 [21:10]: 0x7E0 = 2016
  - Rn [9:5]: 29 (X29)
  - Rt [4:0]: 10 (X10)
  - Offset: 2016 * 8 = 16128 bytes
```

STR would have opcode 0xF8, but this is 0xF9 (LDR).

### 2. Source of Corrupted Instructions

Added comprehensive debug logging to track instruction generation:

```c
// In arm_ldr_imm()
if (imm12 > 10) {
    fprintf(stderr, "[DEBUG arm_ldr_imm] rt=%d rn=%d imm12=%d size=%d inst=0x%08x offset=%d\n",
            arm_reg(rt), arm_reg(rn), imm12, size, inst, imm12 * (1 << size));
}

// In arm_str_imm()
if (imm12 > 10) {
    fprintf(stderr, "[DEBUG arm_str_imm] rt=%d rn=%d imm12=%d size=%d inst=0x%08x offset=%d\n",
            arm_reg(rt), arm_reg(rn), imm12, size, inst, imm12 * (1 << size));
}
```

**Result:** NO calls to `arm_ldr_imm()` or `arm_str_imm()` with:
- `imm12=2016` (offset 16128)
- `rn=29` (X29/frame pointer)

**Conclusion:** The corrupted instructions are NOT being generated by the standard LDR/STR helper functions!

### 3. Suspicious Offset Values

The offsets 16128 and 16096 decode to:
- 16128 / 8 = 2016 = 0x7E0
- 16096 / 8 = 2012 = 0x7DC

These look like **array indices** or **large field offsets**, not stack offsets.

Normal ARM64 stack frames are 32-144 bytes, not 16KB!

### 4. Previously Fixed Bugs

Before discovering the corruption issue, fixed two critical opcode bugs:

**Bug #1: LDUR opcode (FIXED, committed)**
- Location: `src/jit.c:6668`
- Problem: Used 0x38 (STUR/store) instead of 0x39 (LDUR/load)
- Fix: Changed to 0x39, bit 22 = 1 for load
- Result: Arguments now load correctly, X0 contains valid pointers

**Bug #2: STR opcode (FIXED, committed)**
- Location: `src/jit.c:6658`
- Problem: Used 0x39 (LDR/load) instead of 0x38 (STR/store)
- Fix: Changed to 0x38, bit 24 = 0 for store
- Result: Store instructions now generate correct opcode

## Possible Corruption Sources

### Theory 1: Jump Patching Gone Wrong
The `arm_patch_branch()` function modifies branch instructions after generation. If positions are calculated incorrectly, it could overwrite non-branch instructions.

**Evidence against:** Patching only modifies offset bits of existing branch instructions, shouldn't create new LDR/STR opcodes.

### Theory 2: Buffer Overflow
JIT code buffer might be too small, causing later functions to overwrite earlier ones.

**Evidence against:** Last function at offset 0x17ee4 with reasonable framesizes (32-112 bytes).

### Theory 3: Direct B32() Calls
Some code path might be calling `B32()` with pre-computed instruction values that are incorrect.

**Next step:** Search for direct `B32()` calls with computed values.

### Theory 4: Data Being Executed as Code
The corrupted bytes might be data (constants, addresses) that accidentally got placed in the code section and are being executed.

**Supporting evidence:** The pattern of repeated instructions and huge offsets doesn't match any logical code generation.
