# ARM64 JIT Memory Corruption - ROOT CAUSE IDENTIFIED

## Status: **CRITICAL BUG FOUND** ✅

**Date:** 2025-11-19
**Investigation Method:** Static code analysis (Option B: Targeted Code Review)
**Time to Find:** ~1 hour of systematic review

---

## The Bug

**ARM64 JIT code is using `BUF_POS()` instead of `ARM_BUF_POS()` throughout the codebase, causing buffer position tracking to become desynchronized and resulting in jump patching corruption.**

---

## Technical Explanation

### Buffer Structure (src/jit.c:503-509)

```c
struct jit_ctx {
    union {
        unsigned char *b;      // Byte pointer (used by x86)
        unsigned int *w;       // Word pointer (used by ARM64)
        unsigned long long *w64;
        int *i;
        double *d;
    } buf;
    // ...
}
```

This is a **union** - all pointers share the same memory address but have different types.

### The Two Macros (src/jit.c:190, 332)

```c
#define BUF_POS()       ((int)(ctx->buf.b - ctx->startBuf))
#define ARM_BUF_POS()   ((int)((unsigned char*)ctx->buf.w - ctx->startBuf))
```

**Key Difference:**
- `BUF_POS()` uses `buf.b` (byte pointer)
- `ARM_BUF_POS()` uses `buf.w` (word pointer, cast to bytes)

### How Instructions Are Written

**x86 Code:**
```c
#define B(bv)  *ctx->buf.b++ = (unsigned char)(bv)
// Writes 1 byte, increments buf.b by 1
```

**ARM64 Code:**
```c
#define B32(val)  *ctx->buf.w++ = (unsigned int)(val)
// Writes 4 bytes, increments buf.w by 4 bytes
```

### The Desynchronization Problem

1. **Initialization** (src/jit.c:569, 735):
   ```c
   ctx->buf.b = nbuf + curpos;
   ```
   Sets `buf.b`. Since it's a union, `buf.w` gets the same address.

2. **ARM64 Writes Instructions**:
   ```c
   B32(0xd10083ff);  // ARM64 instruction
   // This increments buf.w by 4 bytes
   // buf.b is NOT updated (it's a separate union member)!
   ```

3. **Later Code Calls BUF_POS()**:
   ```c
   ctx->opsPos[opCount] = BUF_POS();
   // Returns buf.b - startBuf
   // But buf.b hasn't moved! It's still at the OLD position!
   // buf.w is at the CURRENT position!
   ```

4. **Result**:
   - `opsPos[]` contains INCORRECT (too-small) positions
   - Jump patching uses these positions to write branch offsets
   - Patches write to WRONG memory locations
   - Random instructions get corrupted!

## Why This Causes the Reported Symptoms

### Symptom 1: Huge Offsets (16KB+)
- Jump target position stored as (e.g.) 100 instead of 16000
- Jump source position stored correctly as 16000
- Offset = target - source = 100 - 16000 = **-15900**
- When encoded as unsigned, this becomes a huge positive offset
- Results in instructions like `ldr x10, [x29, #16128]`

### Symptom 2: Repeated Instructions
- Jump patching writes to wrong location (position 100 instead of 16000)
- Overwrites unrelated instructions early in the buffer
- Some instructions get partially overwritten multiple times
- Results in repeated `mov x29, sp` patterns

### Symptom 3: No Debug Output from LDR/STR Functions
- The corrupted instructions are NOT generated by `arm_ldr_imm()` or `arm_str_imm()`
- They're created by jump patching writing to WRONG buffer positions
- Debug logging in helper functions never triggered (as reported)

## The Fix

### Simple Fix: Use ARM_BUF_POS() Everywhere

Replace ALL occurrences of `BUF_POS()` within ARM64 code paths with `ARM_BUF_POS()`.

**Specific Changes Needed:**

1. **Line 3382-3388** (Alignment):
   ```c
   - while (BUF_POS() & 3) {
   + while (ARM_BUF_POS() & 3) {
   ```

2. **Line 3853** (Function pointer):
   ```c
   - m->functions_ptrs[f->findex] = (void*)(int_val)BUF_POS();
   + m->functions_ptrs[f->findex] = (void*)(int_val)ARM_BUF_POS();
   ```

3. **Line 3603** (Size):
   ```c
   - int size = BUF_POS();
   + int size = ARM_BUF_POS();
   ```

4. **Line 3614** (memcpy):
   ```c
   - memcpy(code,ctx->startBuf,BUF_POS());
   + memcpy(code,ctx->startBuf,ARM_BUF_POS());
   ```

5. **Line 3702** (Cache flush):
   ```c
   - __builtin___clear_cache((char*)code, (char*)code + BUF_POS());
   + __builtin___clear_cache((char*)code, (char*)code + ARM_BUF_POS());
   ```

6. **Line 3918** (opsPos - **MOST CRITICAL**):
   ```c
   for(opCount=0;opCount<f->nops;opCount++) {
       // ...
   -   ctx->opsPos[opCount + 1] = BUF_POS();
   +   #ifdef HL_JIT_ARM64
   +   ctx->opsPos[opCount + 1] = ARM_BUF_POS();
   +   #else
   +   ctx->opsPos[opCount + 1] = BUF_POS();
   +   #endif
   }
   ```

7. **Line 3908** (opsPos[0]):
   ```c
   - ctx->opsPos[0] = BUF_POS();
   + #ifdef HL_JIT_ARM64
   + ctx->opsPos[0] = ARM_BUF_POS();
   + #else
   + ctx->opsPos[0] = BUF_POS();
   + #endif
   ```

## Alternative Fix: Synchronize buf.b After Every B32()

Could modify the `B32()` macro to also update `buf.b`:

```c
#define B32(val) do { \
    *ctx->buf.w++ = (unsigned int)(val); \
    ctx->buf.b = (unsigned char*)ctx->buf.w; \
} while(0)
```

**Pros:** Keeps BUF_POS() working for both x86 and ARM64
**Cons:** Performance overhead (extra assignment for every instruction)

## Why This Bug Was Hard to Find

1. **Subtle C Union Behavior:** Union members aren't automatically synchronized
2. **Macro Indirection:** `BUF_POS()` looks innocent, hides pointer choice
3. **Shared Code Path:** Line 3918 is shared between x86 and ARM64
4. **Non-obvious Symptom:** Manifests as instruction corruption, not pointer bugs
5. **Works on x86:** Bug only affects ARM64, so it went unnoticed
