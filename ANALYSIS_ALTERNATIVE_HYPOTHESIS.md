## Problem with "Bytecode Truncation" Theory

The BYTECODE_TRUNCATION_ROOT_CAUSE.md concludes that `0xf5c433ed` is stored in the bytecode's `ints[]` array. **This conclusion has a fundamental logical flaw:**

### Why JIT Pointers Cannot Be in Bytecode

1. **JIT compilation happens at runtime**
   - Bytecode is generated by Haxe compiler
   - JIT buffer address `0x7ffff5c34000` is allocated at runtime
   - Offset `0xf5c433ed` is computed during JIT compilation
   - **These values don't exist when bytecode is created**

2. **Bytecode is platform-independent**
   - `.hl` files can run on x86, ARM64, etc.
   - They cannot contain platform-specific memory addresses
   - Function addresses are resolved at runtime, not compile time

3. **The crash context doesn't match**
   - Crash: `hl_hbset_impl` receives bad pointer in x0
   - Function: bytes map set operation (NOT a function pointer operation)
   - Expected x0: pointer to `hl_bytes_map` object
   - Actual x0: `0xf5c433ed` (interpreted as JIT function address)

## Alternative Theories

### Theory 1: Object Pointer Corruption

**Hypothesis:** An `hl_bytes_map*` object pointer gets corrupted/truncated before being passed to `hl_hbset_impl`.

**How this could happen:**
1. Object allocated on heap at address `0x7fff_something`
2. Pointer stored in a vreg or object field typed as HI32
3. Field offset calculation uses wrong size (4 instead of 8)
4. Adjacent field overwrites upper 32 bits
5. Corrupted pointer loaded and passed to native function

**Evidence needed:**
- Check if any `hl_bytes_map*` is stored in an HI32-typed field
- Verify object field layouts at runtime
- Add debug logging when storing/loading map pointers

### Theory 2: Vreg Stack Corruption

**Hypothesis:** The vreg containing the map pointer has wrong stack offset.

**How this could happen:**
1. HI32 vreg allocated with `stackPos` calculated for 4-byte slot
2. 64-bit pointer stored with STORE_VREG (size=3)
3. Upper 32 bits overflow into next vreg
4. LOAD_VREG reads from wrong offset
5. Loads garbage or partial value

**Evidence needed:**
- Check `r->stackPos` calculation in jit.c
- Verify stack frame layout matches vreg sizes
- Add debug logging in LOAD_VREG/STORE_VREG for HI32

### Theory 3: Field Offset Miscalculation

**Hypothesis:** Object field offsets don't match between constant initialization and JIT access.

**How this could happen:**
1. `hl_module_init_constant` initializes object with T_SIZES[HI32]=8
2. JIT code computes field offsets differently (uses 4?)
3. Load from field X actually reads from field X+1
4. Wrong data loaded, appears as truncated pointer

**Evidence needed:**
- Compare field offset calculation in module.c vs jit.c
- Check if OField opcode uses hl_type_size() or cached offsets
- Verify rt->fields_indexes matches what JIT expects

### Theory 4: The Value Isn't a Pointer At All

**Hypothesis:** `0xf5c433ed` is actually an integer constant that coincidentally falls in JIT buffer range.

**How this could happen:**
1. HI32 integer constant with value `0xf5c433ed` in bytecode
2. Incorrectly used where a pointer is expected
3. Type confusion in the Haxe code or compiler

**Evidence needed:**
